# 정적 데모 구현 체크리스트

## 1. 범위 확정

- [x] 데모의 핵심 흐름을 `성향 선택 → 매칭 조건 선택 → 매칭 성공 → 채팅 체험`으로 제한한다.
- [x] 회원가입, 로그인, 마이페이지, 관리자, 신고, 후기 기능은 제외한다.
- [x] 실제 AI 추천, 실시간 매칭, WebSocket 연결은 제외한다.
- [x] 데모가 실제 서비스가 아닌 고정 시나리오임을 명시한다.
- [x] 데모 완료 조건과 초기화 조건을 정의한다.

## 2. 프로젝트 구조

- [x] 기존 `frontend` 프로젝트 안에 `demo.html`을 추가한다.
- [x] `frontend/src/demo/main.js`를 생성한다.
- [x] `frontend/src/demo/scenario.js`를 생성한다.
- [x] 필요한 경우에만 `frontend/src/demo/demo.css`를 추가한다.
- [x] 기존 `style.css`, 이미지, 브랜드 자산을 재사용한다.
- [x] 운영용 `main.js`에서 데모 코드를 불러오지 않도록 분리한다.

```text
frontend/
├─ index.html
├─ demo.html
├─ src/
│  ├─ main.js
│  ├─ style.css
│  └─ demo/
│     ├─ main.js
│     ├─ scenario.js
│     └─ demo.css
├─ dist/
└─ dist-demo/
```

## 3. 데모 시나리오 데이터

- [x] 가상 사용자 이름, 프로필, 성향 데이터를 작성한다.
- [x] 음식 유형별 고정 매칭 결과를 작성한다.
- [x] 지역, 시간, 희망 성향 선택 데이터를 작성한다.
- [x] 고정 채팅 메시지를 작성한다.
- [x] 추천 식당 샘플 데이터를 작성한다.
- [x] 실제 사용자 정보로 오해할 수 있는 데이터를 배제한다.
- [x] 동일한 입력은 항상 동일한 결과가 나오도록 구성한다.

## 4. 화면 흐름

- [x] 데모 시작 화면을 구현한다.
- [x] 식사·대화 성향 선택 화면을 구현한다.
- [x] 지역·음식·시간 선택 화면을 구현한다.
- [x] 매칭 검색 애니메이션을 구현한다.
- [x] 가상 상대 프로필과 매칭 이유를 표시한다.
- [x] 수락 버튼을 통한 매칭 완료 처리를 구현한다.
- [x] 고정 메시지를 사용하는 채팅 체험을 구현한다.
- [x] 추천 식당 또는 약속 장소를 표시한다.
- [x] `처음부터 다시 체험` 버튼을 구현한다.
- [x] 잘못된 경로로 접근하면 데모 시작 화면으로 이동한다.

## 5. 데모 상태 관리

- [x] 상태를 다음과 같은 단순한 단계 값으로 관리한다.

```text
START
→ PERSONALITY
→ CONDITIONS
→ SEARCHING
→ PROPOSAL
→ CHAT
→ COMPLETE
```

- [x] 필요한 경우 `sessionStorage`에 진행 상태를 저장한다.
- [x] 저장 키를 `majuhankki.demo.v1`처럼 운영 키와 분리한다.
- [x] 초기화 시 데모 저장 데이터만 삭제한다.
- [x] 운영용 `project2.isLoggedIn` 값을 사용하지 않는다.
- [x] Access Token이나 가짜 JWT를 생성하지 않는다.

## 6. 운영 서비스와 격리

- [x] 운영 API로 `fetch` 요청을 보내지 않는다.
- [x] `/auth`, `/users`, `/matches`, `/chatrooms`를 호출하지 않는다.
- [x] `/ws-chat` WebSocket에 연결하지 않는다.
- [x] 운영 쿠키를 읽거나 변경하지 않는다.
- [x] 운영 DB, Redis, Spring Security 설정을 변경하지 않는다.
- [x] 데모를 위해 `permitAll()` 범위를 확대하지 않는다.
- [x] 실제 위치나 개인정보를 수집하지 않는다.
- [x] 외부 지도 API 사용 여부를 명확히 결정한다.

## 7. 데모 표시와 UX

- [x] 모든 화면에 `체험용 데모` 배지를 표시한다.
- [x] `실제 사용자와 연결되지 않습니다` 안내를 표시한다.
- [x] 실제 매칭처럼 오해할 수 있는 문구를 제거한다.
- [x] 검색 대기 시간을 1~2초 정도로 제한한다.
- [x] 모바일과 데스크톱에서 사용할 수 있도록 구성한다.
- [x] 키보드 탐색과 버튼 포커스를 제공한다.
- [x] 애니메이션 감소 설정을 고려한다.
- [x] 오류가 발생해도 시작 화면으로 복구할 수 있게 처리한다.

## 8. Vite 빌드 분리

- [x] `vite.config.js`에 데모 모드 입력 파일을 설정한다.
- [x] 운영 출력 경로를 기존 `dist`로 유지한다.
- [x] 데모 출력 경로를 `dist-demo`로 설정한다.
- [x] `package.json`에 데모 빌드 명령을 추가한다.

```json
{
  "scripts": {
    "build": "vite build",
    "build:demo": "vite build --mode demo"
  }
}
```

- [x] 데모 빌드에 운영 API URL이 포함되지 않는지 확인한다.
- [x] 기존 `npm run build` 결과가 변하지 않는지 확인한다.
- [ ] 데모 호스팅의 SPA fallback 경로를 설정한다.

## 9. 환경변수

- [x] 데모에 불필요한 환경변수를 추가하지 않는다.
- [x] 지도 API가 필요하면 데모 전용 키를 사용한다.
- [x] 지도 키에 데모 도메인 제한을 적용한다.
- [x] 환경변수를 추가하면 `.env.sample`에 빈 값 또는 예시 값을 추가한다.
- [x] 실제 키나 자격증명을 저장소에 커밋하지 않는다.

## 10. 검증

- [x] `npm run build`가 성공한다.
- [x] `npm run build:demo`가 성공한다.
- [x] 로그인하지 않은 시크릿 창에서 전체 데모를 완료할 수 있다.
- [x] 브라우저 Network 탭에서 운영 API 요청이 없는지 확인한다.
- [x] WebSocket 연결이 생성되지 않는지 확인한다.
- [x] 운영 쿠키와 세션 값이 변경되지 않는지 확인한다.
- [x] 새로고침 시 정의한 방식대로 상태가 유지되거나 초기화되는지 확인한다.
- [x] `처음부터 다시 체험`이 정상 작동하는지 확인한다.
- [x] 모바일 화면에서 주요 버튼이 가려지지 않는지 확인한다.
- [ ] 운영 프런트의 로그인, 매칭, 채팅 기능이 그대로 동작하는지 확인한다.

- [ ] 운영 배포와 데모 배포 파이프라인을 분리한다.

## 완료 조건

- [x] 비로그인 사용자가 데모 흐름을 처음부터 끝까지 체험할 수 있다.
- [x] 데모 진행 중 운영 API, 쿠키, DB, Redis, WebSocket에 접근하지 않는다.
- [ ] 운영 서비스의 빌드와 기존 기능에 회귀가 없다.
- [x] 데모 화면에서 실제 서비스가 아닌 체험용 시나리오임을 명확하게 알 수 있다.
